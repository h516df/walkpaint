# v0.41 验收与交付证据

**本轮唯一目标来自用户原话**：「真机高德没验过……这个你要解决，因为你的测试和真机不一样，所以你永远有问题。」

这句话是对的。本轮不去辩解"测试也差不多"，而是把两件事一起做完：
1. **证明本机根本跑不了高德**——这样"模拟器通过"再也不会被当成"高德通过"；
2. **让用户的手机自己把高德的实况交出来**——这是唯一能真正结束"永远有问题"的做法。

## 一、本机为什么验不了高德：两条硬证据

### 1. 高德 SDK 的原生库只有 ARM，没有 x86/x86_64

直接列**已发布**的 `dist/v0.40/input/WalkPaint-v0.40-universal.apk` 里的 `lib/`（不是看源码推断，也不看 Gradle 声明）：

| ABI | 内容 |
|---|---|
| `arm64-v8a` | `libAMapSDK_MAP_v11_3_100.so`(34.5 MB)、`libapssdk.so`、`libmaplibre.so`、`libandroidx.graphics.path.so` |
| `armeabi-v7a` | `libAMapSDK_MAP_v11_3_100.so`(23.6 MB)、`libapssdk.so`、`libmaplibre.so`、`libandroidx.graphics.path.so` |
| `x86` | 只有 `libmaplibre.so` + `libandroidx.graphics.path.so` |
| `x86_64` | 只有 `libmaplibre.so` + `libandroidx.graphics.path.so` |

也就是说：x86_64 模拟器上**装得上、跑得起来**的只有 MapLibre 备用地图，高德那一路在这个 ABI 上连代码都没有。
`AmapPlatform.supported()` 正是按 `SUPPORTED_ABIS` 首选 ABI 做这个判断，所以模拟器上 `amapActive=false` 是**正确行为**，不是配置失误。

### 2. 模拟器拒绝在 x86_64 主机上跑 arm64 镜像

既然 x86 没有高德库，唯一设想过的替代路线是"装一个 arm64 模拟器，在里面跑真的高德"。为此下载了 `system-images;android-34;google_apis;arm64-v8a` 并建了 AVD（脚本 `scripts/try_arm64_emulator.py`，含创建→启动→等 boot→打印日志尾部）。模拟器自己的回答（原始日志 `verification/arm64-emulator.log`）：

```
INFO         | Found systemPath D:\Apps\Android\sdk\system-images\android-34\google_apis\arm64-v8a\
FATAL        | Avd's CPU Architecture 'arm64' is not supported by the QEMU2 emulator on x86_64 host. System image must match the host architecture.
```

进程随即以非零码退出，`adb devices` 里始终没有 `emulator-5558`。（`emulator/qemu/windows-x86_64/` 下确实有 `qemu-system-aarch64.exe`，但 Android 模拟器不允许用它跑 arm64 AVD。）

### 结论

| 路线 | 能否验证高德 | 依据 |
|---|---|---|
| x86_64 AVD（现有测试环境） | ❌ | 高德无 x86/x86_64 原生库 |
| arm64 AVD | ❌ | 模拟器 FATAL：x86_64 主机不支持 arm64 镜像 |
| JVM 单元测试 | ❌ | 只能验纯逻辑，验不了高德 SDK 的渲染与图层 |
| **ARM 真机（用户的手机）** | ✅ | 唯一可行；高德有 arm64 库 |

**因此：在用户手机上取得证据之前，任何关于高德路径的结论都不能宣称已验证。** 本轮不再产出这类结论，而是改为让手机自己报告。

## 二、这一版做了什么：把"高德到底怎么了"变成手机能回答的问题

### A. 导出里新增「引擎判定」与「引擎明细」

`VeilReport.engineChoice()` + `AmapMapController.describe()` / `MainActivity.mapEngineDetail()`：

```
引擎判定=没有用高德 本机首选ABI=x86_64 高德支持本机=否（高德只提供 ARM 库） 高德Key=已配置 高德隐私同意=是
备用地图=样式已加载 图层共N个 雾图层=序号i 雾图源=有 行走线图层=序号j 雾在行走线下面=是 雾图版本=37
```

在高德真机上同一位置会变成：

```
引擎判定=正在用高德 本机首选ABI=arm64-v8a 高德支持本机=是 高德Key=已配置 高德隐私同意=是
高德=视图已建 地图加载完成=true 地面图层有(位图=512x512 图层版本=37 边界=…) 折线=描边2条/芯2条(zIndex 10/11，地面图层zIndex 9) 坐标换算缓存=412 手势挂起=false
```

这一段专治三种**从外部看起来完全一样**的故障：

| 现象 | 手机报告会写 |
|---|---|
| 高德根本没启用（ABI/Key/未同意） | `引擎判定=没有用高德 …高德支持本机=否` |
| 高德启用了，但地面图层没建起来 | `地面图层没有（位图已交给高德 512x512，但地面图层没建起来）` |
| 高德建了图层，但底图画在雾上面 | `地面图层有(…)` + `雾位图=…不透光=99%` → 图层没问题，问题在渲染顺序 |

只有第三种需要换掉"用一张位图盖住地图"的做法，前两种根本不用动渲染代码。**在拿到手机报告之前不动渲染层，是因为那会是在猜。**

### B. 导出里新增迷雾的像素实测

`VeilReport.of(IntArray)` 把雾图分四档计数，导出一行：

```
雾位图=262144像素 不透光=93.1% 其中纯黑=93.1% 半透=0.2% 透出地面=6.7% 版本=37
```

`不透光` 与 `其中纯黑` 必须分开报：alpha 255 的深蓝雾同样"不透光"，但那不是用户要的效果——用户原话「雾气很淡，螚够透过黑雾看到地图的线路」正是这两件事的混合。分开之后，"雾本身画淡了"和"地图把底图画在雾上面"就变成了两个互斥的、可判定的结论。

### C. 导出会解释「打开没雾、放大才有」

`VeilReport.frame()` 报每米像素、走廊像素，并在 30 米通道不足 2 像素时明说：

```
雾帧=512x512像素 覆盖纬度74.4° 经度74.4° 每米=0.000像素 走廊=2.0像素（已到2像素下限，这一帧太宽，画不出走廊） 地图画行走线=是
```

启动瞬间地图还没报告投影，用的是 60° 兜底大帧；60° 铺到 512 像素上，30 米通道连一个像素都不到——这句话把用户第一句抱怨（「点开 App 后，没有黑雾遮挡地图」）从感觉变成了算术。同一行在街道级会显示 `每米=0.6像素 走廊=18像素 地图画行走线=否`，两种状态一眼可分。

### D. 手机可以把现场交出来（不必手抄）

```
adb shell am start -n cn.walkpaint/.MainActivity --ez cn.walkpaint.extra.EXPORT_FIELD_REPORT true
```

应用会把导出写到自己的外部目录，并用 logcat `WalkPaintField` 打出绝对路径（这样读的一侧不用去猜 `/sdcard` 与 `/storage/emulated/0`，也不用管多用户）。**只有显式发这条命令才会生成文件**，内容与用户手动点「导出记录现场」看到的完全相同，不上传。`MainActivity` 因此改为 `singleTop`。

### E. 新增真机验收通道 `scripts/phone_acceptance.py`

接上手机后一条命令：

```
python -X utf8 scripts/phone_acceptance.py --apk dist/v0.41/input/WalkPaint-v0.41-universal.apk
```

它按顺序做：ABI 核对 → APK 内 ABI 核对 → 安装 → 授权（精确/后台/通知）→ 启动截图 → 从 logcat 取「记录现场」→ 判定。以下情况**显式失败并说明原因**，绝不返回一个看着通过的结果：

- 手机不是 arm64 → 直接说明它同样跑不了高德，退出码 2；
- APK 里没有 `arm64-v8a` → 拒绝当作高德验收；
- 导出没取到 → 明说"没有它这次运行就无法说明是哪套引擎"，退出码 4；
- 手机上没跑在高德（`引擎判定=正在用高德` 不出现）→ 指出截图结果描述的是备用地图，并提示高德需要 ARM 构建 + Key + 用户一次性同意；
- 高德在跑但 `地面图层没有` → 指出连雾都没建起来；
- 屏幕黑雾比例 < 0.05 → "未知区域仍可读"，退出码 4。

### F. 修掉验收脚本自身的判据分叉

`android_fog_line_acceptance.py` 里"什么算雾"的谓词原本是深蓝判据（`b > g and b > r`）。雾在 0.39 改成纯黑之后，纯黑**永远不匹配**这个谓词——那次 `veil_ratio 0.001` 的失败是我的测量 bug，不是渲染 bug（当时的核实方式：拉出应用自己 dump 的位图，与截图逐项比对）。这件事原本记在 `V039.md`，本轮把判据抽成 `scripts/veil_measure.py`，**两条通道共用同一套阈值与同一个分类函数**，避免"模拟器通过"和"真机通过"的标准悄悄分叉。

抽取正确性用 5 万个随机像素对新旧两套实现逐位对拍：

```
new {'veil_ratio': 0.001, 'bare_map_ratio': 0.052, 'tint_ratio': 0.136}
old {'veil_ratio': 0.001, 'bare_map_ratio': 0.052, 'tint_ratio': 0.136}
EQUIVALENT
```

## 四、目标路径未验收 —— 高德真机

**状态：未验收。** 原因见 §一：本机（x86_64 + Windows）不存在能运行高德 SDK 的运行时。

这一条按工作区规则显式记录，不使用"模拟器通过"替代：
- 本轮在模拟器上验证的是 **MapLibre 备用地图** + **共享的迷雾位图生成** + **导出内容**；
- 高德路径的**控件层级、GroundOverlay 合成顺序、真机 GNSS 行为**均未验证；
- 用户原话的落点（真机高德观感）因此仍悬空，直到手机给出「记录现场」。

需要用户配合的最小动作（二选一，任一即可）：
1. 装上 0.41 后打开「我的 → 更多设置 → 诊断与反馈 → 导出记录现场」，把内容发我；
2. 用 USB 或无线调试把手机连一次电脑（`adb devices` 能看到即可），之后每次更新我都能自己取回现场，用户不必再动手。

## 五、隐私与边界

- 「记录现场」含行走坐标。它**不自动上传**；本轮新增的文件写出同样只在**显式命令**下发生，且写到应用自己的外部目录（同机、同应用），不经过网络。
- 导出内容里不含高德 Key，只写"已配置/未配置"；不含密码、token、Cookie。
- 常驻诊断（`RecordingDiagnostics`）仍然只存原因码、不含坐标。
- `verification/` 与 `dist/` 均在 `.gitignore` 内，现场材料不进 Git。
