## 一、先纠正我上一轮写错的结论

上一轮我写下「本机永远无法验证高德」，依据是两条当时为真的观察。**这个结论错了一半，错的那一半正好是关键的**：

| 观察 | 是否成立 |
|---|---|
| 高德原生库只有 `arm64-v8a` / `armeabi-v7a`（列已发布 universal APK 的 `lib/`） | ✅ 成立 |
| arm64 **系统镜像**在本机被模拟器拒绝：`FATAL \| Avd's CPU Architecture 'arm64' is not supported by the QEMU2 emulator on x86_64 host.` | ✅ 成立 |
| ~~因此本机跑不了高德~~ | ❌ **不成立** |

真正的原因在 App 自己身上：`AmapPlatform.supported()` 只看 `SUPPORTED_ABIS.first()`（本机 AVD 是 `x86_64`），于是永远回退到 MapLibre。而 Google 的 API 30+ x86_64 镜像 **自带 ARM 原生桥**：`ro.product.cpu.abilist=x86_64,arm64-v8a`、`ro.enable.native.bridge.exec=1`、`libndk_translation.so` 与 GLES 代理齐全。装 **arm64-only** 包时，装包器按整个 ABI 列表选 `arm64-v8a`，进程真的加载 ARM 库，走翻译层执行。

**根本教训写进测试**：旧 `AmapPlatformTest` 把这条件写死成 `assertFalse(supported(listOf("x86_64","arm64-v8a")))`——测试把错误的假设锁住了。已改正，并保留 x86 无桥时仍拒绝。

## 三、首屏迷雾：根因与修复（用户诉求 1）

### 根因是算术，不是渲染

雾图长边上限 512 像素，所以**帧越宽越粗**。启动瞬间引擎还没上报视图，用的是 60° 兜底帧：30 米通道摊到 512 像素上只有 **0.002 像素**；而描边有 **2 像素下限**，于是"比一个像素还细"被画成 2 像素宽的通道——60° 帧上的 2 像素是**三十多公里**的地面被当成"已走过"。在街道级首屏（屏幕只显示几十米）上，这条带子覆盖整屏，于是**打开就是完整底图，缩小/放大后才看见雾**。

### 修复：图像要么画出真实宽度的通道，要么不画

- 新增并统一谓词 `TrailPaint.corridorVisible(frame)`：`30 米 × 每米像素 ≥ 2`。不成立时**完全不描通道**（图全黑），由地图自己画"走过的线"作为记录——UI 判断画不画线用的是同一个谓词，两者不可能分叉。
- 去掉 2 像素下限（`core`/`feather` 不再 `coerceAtLeast`）。不变式：**雾图绝不显示比真实通道更宽的地面**。
- 空数据也要有雾：以前"没有任何路径"直接 `return bitmap`（不画），新用户首屏看到完整底图，是同一缺陷的另一面。现在照画全黑帧。
- 但"空输入"不等于"没变化"：重用缓存的跳过条件加上 `!paintedCorridor`——**先走过、随后数据清空**时必须把旧通道擦掉，否则旧图会被继续端出去（复核指出的具体回归）。
- 视口合理性上限 60° → **170°**：以前把用户真实的一次宽视野缩小当成"引擎没就绪"丢掉，于是退回以人为中心的帧，屏幕边缘露出底图。现在真实视野一律成帧（帧 = 视野 + 35%），宽视野因谓词不画通道而仍然全黑。

### 本机可验部分

- JVM：`CorridorRevealTest` 4 例——启动帧不可画通道、街道帧可画且宽度 ≥2 像素、阈值恰在 2 像素、空数据仍产出覆盖视野的帧。
- 像素级（`FogPixelProbe`，真 Bitmap）：新增第 9/10/11 项——**启动帧不得透出任何采样像素**、**30 公里宽视野不得透出**、**清空数据必须擦掉旧通道**（复用同一个 painter，否则新 painter 会空过跳过逻辑）。
- 真实高德引擎上的像素统计（本轮实测）：`雾位图=197632像素 不透光=100.0% 其中纯黑=100.0% 半透=0.0% 透出地面=0.0%`。

## 四、高德坐标基准（独立复核发现的第二个高风险差异）

`AmapMapController.viewport()` 以前把高德 `projection.visibleRegion` 的坐标**直接当 WGS84 返回**，而 `TrailPaint`/`MainActivity` 的契约是 WGS84，`syncGround()` 又对同一帧四角调 `toAmap()` 二次换算；`focusBounds()` 也把原始 WGS84 丢给高德。中国境内偏差数百米，而项目唯一的荚具在**巴黎**（48.856/2.35，偏置为恒等），所以本机检查一直通过。

修复：新增 `CnCoordinate`（公开算法的正向变换 + 数值迭代反解，15 轮收敛到亚厘米），`viewport()` 反解回 WGS84，`focusBounds()` 走同一 `toAmap()`。
本轮实测（中国荚具）：WGS84 可见中心距荚具 **1 米**，引擎中心与它相差 **481 米**——既不是 0（漏换算），也不是 ~960 米（重复换算）。

JVM：`CnCoordinateTest` 6 例（巴黎恒等、中国城市确有数百米偏移、往返 <1 厘米、边界外不动、`shiftMetres` 一致）。

## 七、本轮发现但未修的缺陷（显式留在记录里）

- `PlaceName` 直接用 `com.amap.api.services.geocoder.GeocodeSearch`，**未先调用**高德"服务"SDK 的隐私合规接口（`ServiceSettings.updatePrivacyShow/updatePrivacyAgree`）。logcat 实录：
  `com.amap.api.services.core.AMapException: ***确保调用SDK任何接口前先调用更新隐私合规updatePrivacyShow、updatePrivacyAgree两个接口并且参数值都为true，若未正确设置有崩溃风险***`
  影响：即使地图引擎选的是备用地图，仍会构造高德搜索对象（未同意也可能发起请求，且有崩溃风险）。本轮只记录与定位，未改——它属于"同意与隐私边界"，需要单独一轮处理。
- 主机内存紧张时模拟器可能被系统回收（本轮发生过一次），验收脚本因此需要重跑准备。

结论：**已发布 v0.43 的"高德真的运行"已在产物上验证；它的"中国境内落点"本轮未被独立测出**（需要该产物提供一个原始显示坐标字段，或在底图上做可量化的落点比对）。我这条分支的同类修复在本机测得 1 米（见 §四），但那是**另一份构建**，不能替代对 v0.43 的验收。
